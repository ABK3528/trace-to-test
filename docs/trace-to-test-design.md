# trace-to-test —— 设计

日期：2026-09-28 ｜ 目标仓库：私有 GitHub 仓 `trace-to-test`（新建）｜ 文档语言：中文正文 + 英文代码

## 1. 背景与问题

本机已经跑稳一套「browser-harness(CDP) + Chrome」的浏览器验证能力，主要用途是 **BUG 复现/验证**。
但它现在长在 modelgo 项目里，业务绑定严重，换项目就得重来。本次要把它抽成一个**业务无关、
可跨项目复用**的框架仓。

盘点下来，真正可抽且已经用真金白银验证过的东西有三样：

| 资产 | 在哪 | 可抽性 |
|---|---|---|
| **browser-harness 的 `events.jsonl` 录制格式** | 三方工具（`browser-use/browser-harness`，uv 装的）自带 `recordings` / `video` | 格式是稳定的数据契约；但**它只录像，不做「录制→可回放回归脚本」** |
| **三段式 UI 自动化架构**（探索 → 固化 → 回归，零 LLM 回放，三态判定） | `tests/ui-harness/`（`probe.json` / `workflow.json` + `checks.json` / `runner.py`） | 架构业务无关，**脚本内容是业务** |
| **一堆假红/假绿判据** | 各处踩坑记录 | 最难重建、最值钱。业务无关的部分必须进机制 |
| **测试全流程提示词**（用例设计六步 + 负控三问 / 任务执行五道闸 / issue 验证门禁 / 看板流转） | `.agent/commands/` 与各 skill | 内核高度业务无关，业务只在「真源在哪、平台 API 长什么样」；需拆成骨架 + 实例片段 |

**核心缺口**：从「一次录制」到「一条能长期回放的回归」之间，没有任何工具。这正是本仓的差异化。

## 2. 目标与非目标

**目标**：产出 `trace-to-test`——一个可移植的 AI 测试框架。机制层零业务词，交付两组东西：

- **机制组**：以一条 UI 竖切（录制 → 编译 → 回放）打通为验收实体；其余三条轨（接口生成 / 流程编排 / 契约）
  在骨架里留位。
- **提示词组**：把测试全流程的提示词提炼成**业务无关骨架 + 项目实例片段**两段式，覆盖
  用例设计 / 任务执行 / issue 验证 / UI 验证四条流程轨。

**非目标（v1 明确不做）**：
- 不做接口测试生成轨、流程编排轨、契约轨的**实现**（只留骨架与 README 占位）。
- 不打包、不 fork `browser-harness` —— 它是**依赖**，不是仓内资产。
- 不做网络代理/录制服务、不引入任何常驻服务。
- 不做视觉回归（像素 diff）；v1 只做语义锚点 + 文本/状态断言。
- 不追求坐标反解 100% 成功；解不出的必须显式暴露（见 §4.1）。

## 3. 决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 覆盖范围 | 全量蓝图 + 分阶段落地，v1 只做 UI 竖切 | 用户拍板；避免在无竖切时先定接口 |
| 仓定位 | **私有**仓，但仍**零业务词** | 用户拍板；私有不等于可以夹带业务，将来若要转公开零返工 |
| v1 靶场 | 仓内自带极简靶场 | 用户拍板；离线可跑、可重复，回归不因外网假红 |
| 以什么为轴心 | 方案 A：以「录制编译器」为轴心 | 直接命中用户的真实用途；机制有端到端证据；其余轨往骨架里填不返工 |
| 仓名 | `trace-to-test` | 用户拍板；自带差异化语义 |
| 文档语言 | 中文正文 / 英文代码与标识符 | 用户拍板；零业务词 grep 不受语言影响 |
| 提示词层的范围 | 不只 UI 轨，把**测试全流程**（用例设计 / 任务执行 / issue 验证 / 看板流转）一并提炼 | 用户要求。这四条轨的核心内核（负控三问、五道闸、实现符合性门禁）恰好高度业务无关，是除机制外第二值钱的资产 |
| 提示词怎么剥离 | **通用骨架 + 项目实例片段**两段式，骨架进仓（占位符化），实例片段由 `adapters/instance/` 注入 | 与机制层同一条边界，可走查、可自检（V7） |

## 4. 架构

### 4.1 分层与业务边界（本设计的第一原则）

| 层 | 目录 | 规矩 |
|---|---|---|
| **机制层** | `core/` `checks/` `skills/` | 🔴 零业务词、零 agent 专属依赖。**唯一需要保证可移植的部分**，`scripts/portability_check.sh` 只扫这三处 |
| **适配层** | `adapters/` | 业务只准活在这里：被测目标声明、账号来源、期望值(oracle)来源、**提示词骨架的实例片段**。仓内只留**接口 + 靶场适配** |
| **提示词层** | `skills/` | 跨 agent 同一份正文，由薄封装分发 |

`core/` 六个模块：`transcript/`（读录制）→ `compile/`（编译成回归）→ `replay/`（确定性回放）
为主链；`primitives/`、`lint/`、`evidence/` 为横向能力。

**可移植性自检**：`grep -riE '<词表>' core/ checks/ skills/` 必须零命中。词表与白名单都写在
`scripts/portability_check.sh` 里：白名单只放 `<target>` 这类占位符，**逐条带理由**；
新增白名单条目等于放宽约束，必须在 MR 里说明。

### 4.2 v1 竖切：录制 → 编译 → 回放

**这条链上有两个语义鸿沟，是本框架存在的全部理由。**

#### 鸿沟一：录制记的是「做了什么」，回归要的是「怎么找到它」

`events.jsonl` 里一条点击长这样：`{"helper": "click_at_xy", "x": 412, "y": 306, "url": "...", ...}`。
坐标写进回归 = 分辨率、字号、布局一变全红。所以 **`compile/` 的真身不是转录器，是「坐标 → 语义锚点」的反解器**。

锚点优先级（高到低）：

| 序 | `by` | 说明 |
|---|---|---|
| 1 | `testid` | `data-testid` 家族属性 —— 显式留给测试的稳定钩子，**最稳** |
| 2 | `role` | `role` + accessible name（button/link/tab/menuitem…） |
| 3 | `text` | 可见文本精确匹配（含 aria-label） |
| 4 | `path` | DOM 结构路径（同级唯一时可用） |
| 5 | `xy` | **兜底，必须带 `"fallback": true`**，lint 报 warning 并在报告里单列 |

**为什么 testid 排第一而不是文本**：文案会随发布变化，拿文案定位会把「按钮没了」和
「按钮改叫别的了」混成一件事。`role`/`text` 类锚点因此标记 `copy_sensitive: true`，
交给 §下方的三态判定处理。

**反解怎么做到**：`events.jsonl` 里**没有目标元素**——`box` 存的是 `activeElement` 的框，
不是被点中的元素。所以锚点只能**在编译期用一次「带探针的回放」重新问浏览器**：
按录制顺序重放，在每个需要锚点的动作**执行之前**用
`document.elementFromPoint(x, y)`（点击类）或 `document.activeElement`（输入/按键类）
取到元素快照，再由纯函数排序器产出候选锚点。**编译器因此复用回放引擎**——
两者是同一个引擎的两种模式：回放模式断言结果，探针模式采集锚点。

需要探针的只有三类动作：`click_at_xy`、`type_text`、`press_key`。
`goto_url`/`new_tab`（有 URL）、`fill_input`/`wait_for_element`（已有 selector）、
`scroll`（页面级）都能直接从事件本身推出，不需要浏览器。

🔴 **反解不出的事件不许默默降级成坐标**：写成 `unresolved.jsonl` 的一条，含原始事件、
候选锚点列表、以及**为什么解不出**。人/agent 补齐后重新编译。这是「录制出来能跑、
换个环境就死」的唯一闸门。

#### 鸿沟二：录到的观测值不能当期望值

把「探索时看到什么」直接写成断言 = oracle 锁错，等于把 bug 固化成基线。
所以 **`compile/` 只产路径 + 观测快照，断言位留空标 `TODO_ASSERT`**；
`checks.json` 里的每条断言**必须带 `source` 字段**声明期望值出处（PRD / 夹具 / 手写），
`lint/` 拒收两类反模式：①无断言 ②`source` 缺失或形如 `observed:*`（即抄观测值）。

#### 回放三态

| 结果 | 判据 | `reason` | 含义 |
|---|---|---|---|
| `PASS` | 全部步骤定位成功且断言通过 | — | 通过 |
| `FAIL_PRODUCT` | 锚点找到了，**断言值不对** | `assertion` | 产品漂移或缺陷 |
| `FAIL_PRODUCT` | 锚点找不到，**但存在近似匹配** | `anchor_drift` | 元素还在，只是标签/文案变了 → 产品改动 |
| `FAIL_ANCHOR` | 锚点找不到，**且无近似匹配** | `missing` / `ambiguous` | 元素没了或结构变了 → 脚本问题 |
| `FAIL_ANCHOR` | 锚点匹配到多个不同元素 | `ambiguous` | 判据不唯一 → 脚本问题 |

**`anchor_drift` 这条是关键**：`role`/`text` 类锚点是 `copy_sensitive` 的，文案一变就找不到。
如果直接判 `FAIL_ANCHOR`，真正的产品文案改动会被误报成「测试写坏了」；反过来若拿坐标兜底，
就退化成 §鸿沟一。所以这里做一次**归一化近似匹配**（去空白/去标点/大小写折叠，
相似度 ≥ 阈值即算命中）：元素还在、只是标签变了 → 归 `FAIL_PRODUCT` 并带 `anchor_drift`；
连近似匹配都没有 → 才归 `FAIL_ANCHOR`。**testid 锚点不做近似匹配**（它没有可比较的文本），
所以锚点失效时直接 `FAIL_ANCHOR`——这正是 V2 两半能分开的原因。

三态划分沿用已验证语义，业务无关，是本套件最值钱的设计之一：它区分「产品坏了」和「测试写坏了」。
**三态是 workflow 的最终结果，只有这三种**——§4.2 的自查项不构成第四态，见下。

**回放路径零 LLM**——模型只在探索期与编译期介入。回放必须能在 CI 上确定性重放。

#### 假红防线

回放判 `FAIL_PRODUCT` 之前，先跑三项自查（业务无关的机制，不是自觉）。这些自查**不改三态定义**，
只决定「现在能不能下结论」：

| 自查 | 命中时 | 不是第四态的理由 |
|---|---|---|
| 目标构建标识与本 workflow 记录的不一致 | 记为 `STALE_TARGET`，**不下产品结论**，报告里标为待确认 | 环境没对齐，此时既不能判产品坏也不能判脚本坏 |
| 首轮失败、次轮通过 | 记为 `COLD_START_FLAKE`，**重跑一次再判** | 重跑后的结果仍归入三态之一 |
| 依赖的探针端点未就绪 | 记 `FAIL_ENV`，与产品问题**分开计** | 只表示「这次没验成」，不表示产品有问题 |

即：`FAIL_ENV` / `STALE_TARGET` 是**「本次未得出结论」**的标注，一条 workflow 只有在环境对齐、
重跑稳定之后产生的结论才落进 `PASS` / `FAIL_ANCHOR` / `FAIL_PRODUCT`。

### 4.3 数据契约（v1 的接口，先定这三个）

**`workflow.json`** —— 纯路径，零断言：

```json
{
  "id": "wf-001-login-and-create-item",
  "title": "登录并创建一条记录",
  "target": "<target-name>",
  "source": {"recording": "<recording-id>", "compiled_at": "<iso8601>", "compiler": "<ver>"},
  "steps": [
    {"n": 1, "action": "goto", "path": "/login"},
    {"n": 2, "action": "fill", "anchor": {"by": "text", "value": "<label>"}, "value_ref": "env:<VAR>"},
    {"n": 3, "action": "click", "anchor": {"by": "role", "role": "button", "name": "<name>"}},
    {"n": 4, "action": "wait_for", "anchor": {"by": "testid", "value": "<id>"}, "state": "visible"}
  ]
}
```

`value_ref` 只允许指向环境变量或适配层声明的凭据名，**禁止把密码/令牌写进 workflow**。

**`checks.json`** —— 断言 sidecar：

```json
{
  "workflow": "wf-001-login-and-create-item",
  "checks": [
    {
      "id": "c1",
      "after_step": 4,
      "kind": "text_present",
      "anchor": {"by": "testid", "value": "<id>"},
      "expect": "<expected>",
      "source": "prd:<path>#<anchor>",
      "observed_at_compile": "<what-was-seen>"
    }
  ]
}
```

`observed_at_compile` 只供编译期人工比对，**永不参与回放判定**。

**`unresolved.jsonl`** —— 每条 = 原始事件 + 候选锚点 + 解不出的原因。

### 4.5 仓内靶场

零依赖 Python 静态服务 + 极简页面，覆盖五件事：**登录**、**异步加载列表**、**弹窗**、
**暗色模式**、**一个可控的偶发失败端点**（专门用来演示三态与假红自查）。
靶场绝不能成为机制层的依赖方向——`core/` 不 import 靶场，靶场只被 `tests/` 与 `make demo` 使用。

### 4.6 提示词层（skills）—— 测试全流程的提炼

测试过程的提示词分两组。**共同的剥离手法是同一条**：每条 skill 拆成
**通用骨架（进仓，业务词全是占位符）+ 项目实例片段（适配层注入）**，
骨架里凡出现「某个具体平台/仓库/真源」的地方一律写成 `<source-of-truth>`、`<platform>`、
`<lane>` 这类占位符，实例片段由 `adapters/` 提供。落地新项目 = 只补实例片段，骨架不动。

#### A 组 · 轨内机制型（有强制力）

挂在已实现的机制上，不是自觉：

| skill | 挂的机制 |
|---|---|
| `explore-anchors` | 探索期怎么选锚点（优先语义，不优先坐标）；`UNRESOLVED` 怎么补 |
| `triage-replay-failure` | 三态怎么复核 —— 假红自查清单（§4.2） |
| `evidence-package` | 证据包规范：截图必须进单、正文逐字验、清 SW 缓存、生产只读原语白名单 |

#### B 组 · 流程型（advisory，诚实标注）

⚠️ **这组没有强制机制**：它们是给 agent 的作业指导，agent 不照做不会有脚本报错。
凡是**能机械化的部分一律下沉成脚本**（见下方「可机械化清单」），剩下真正只能靠判断的
才留在提示词里，并在 skill 头部明写 `advisory: true`。不要把它们写成「必须」，那是自欺。

| skill | 通用骨架（业务无关的内核） | 业务只活在 |
|---|---|---|
| `design-cases` | **六步流程**：① 钉契约真源（**优先级固定**：原型 > 需求文档 > 接口 spec > 单正文；**冲突以高优先级为准且不丢弃**，单列记录 —— 冲突本身往往是真问题线索）② 拆变量（数据/身份/状态/时序/环境 五类）③ 出用例矩阵：**先分轨再铺维度**，分轨判据＝**这条用例的「预期」从哪里读出来**；一条用例只有一个预期来源，跨轨场景拆两条互指 ④ **给每条判据配负控**（核心，见下）⑤ 定级 + 数据策略 + 原子化 ⑥ 落库交接 | 真源具体在哪、平台是哪个、`<lane>` 怎么切 |
| `run-test-task` | **收工前五道闸**（核心，见下）+ 入口硬门（用例地址必须由执行者提供，不接受猜）+ 清单落盘作基线 + 回写双份（团队正本 + 本地原始证据） | 平台 API、字段名 |
| `verify-issue` | PRD 是验收契约最终来源、单正文最低 → 分流（按「预期读自哪里」决定走可自动化轨还是人工轨）→ **测试前强制门禁：实现符合性分析**（逐验收点判 偏离/过度设计/一致，带源码位置证据）→ 读参考 → 写测试 → 执行 → 汇总 → 回写（含符合性分析表）+ 通过时回写状态、不通过改回责任人 | 平台、标签名、责任人判定细节 |
| `board-lifecycle` | 状态机 + 流转判据（谁能推哪一步、什么证据才够推）+ **验通只打「待上线」绝不关单**（关单是另一件事） | 具体列名、标签名 |

**两条最值钱的通用内核**（都是从真金白银踩出来的，且完全业务无关）：

**负控三问**（`design-cases` 的核心）——对每条预期结果连问：

1. **缺陷存在时它会红吗？** 写出让它红的具体数据/实现；写不出 → 删掉重设计。
2. **判据经过被测代码路径吗？** 经过就换**独立真值**。
   > 通则：**当修复手段是「把两个实现合并成一个」时，「两者一致」就不再是有效判据。**
3. **前置可能整批空过吗？** 载具停用/权限门会让一批用例在断言前就返回、集体恒绿。
   > 通则：**一批用例集体因同一前置失败而「绿」，等于集体空过——修好前置后必须重看它们。**

**五道闸**（`run-test-task` 的核心）——全过才算执行完成：

| 闸 | 判据 | 可机械化？ |
|---|---|---|
| ① 覆盖差集 | 清单与结果**双向差集**为空；`pending == 0`；汇报必须有具体数字且六项之和 == total | ✅ 脚本 |
| ② 证据充分性 | 每条 `passed` 要有**实测到的具体值** + **负控结论**；UI 条要有截图路径。只有「符合预期」= 不合格 | 🟡 半 |
| ③ 假绿指纹扫描 | 整批同时绿 / 全批同一错误码却判 passed / 判据用的是被测代码自己的另一个投影 / 「零变化」类判据没配同页正控 | 🟡 半 |
| ④ 失败与阻塞闭环 | 每条 `failed` 有单号；**UI 条截图必须嵌进单内**（只写本地路径＝不合格）；`blocked` 写清缺什么+谁能解除 | ✅ 部分 |
| ⑤ 第二双眼睛 | 派 subagent 复核，**只给入口 URL + 用例 note + 写回结果，不给执行过程与理由**（给了会被锚定，只会复述）；附**禁止清单**（不改任何数据、不开分支、不动看板） | ❌ 解释器 |

**可机械化清单**（B 组下沉成脚本，不许只写在提示词里）：闸①双向差集与计数、
闸②「实测值/负控结论/截图路径」三个字段的存在性检查、闸④「failed 必须有单号」
与「UI failed 必须带嵌图」、以及 §5 V4 的断言反模式 lint。

**reference 文档**（不是 skill，附带进仓，业务无关度极高）：

- `references/coverage-dimensions.md` —— 11 条覆盖维度（等价类/边界值/状态迁移/权限矩阵/
  并发幂等/错误码/i18n/分页排序筛选/审计留痕/数据清理/可达性预检）。
- `references/false-green-catalog.md` —— 假绿指纹目录，按**模式**分类：
  A 判据经过被测路径 / B 样本不能区分实现 / C 只有正控没负控 / D 数据追平与前置塌陷 /
  E 结构性不可达 / F 并发时序 / G 判据打错位置 / H 环境与正控选错 / I 关单后遗留。
  **每条 = 模式 + 通用识别法 + 一个占位符化的反例**，业务实例留在适配层文档里。
- `references/coverage-review.md` —— 覆盖回溯 review：抽需求点清单 → **双向回溯表**
  （需求点→用例 查漏、用例→需求点 查凭空造）→ 独立复核（**差集必须第二双眼睛**，自查抓不到自己的漏）。

## 5. 验收（v1 完成定义，逐项命令可验证）

- **V1 编译可用**：靶场上一条录制能编译出 `workflow.json` + `checks.json`，
  `unresolved.jsonl` 为空或每条均已人工补全并重新编译通过。
- **V2 三态可证**（最硬的一项）：回放绿；**故意改靶场文案** → `FAIL_PRODUCT`；
  **故意移除靶场 DOM 锚点** → `FAIL_ANCHOR`。三种结果都必须由同一条 workflow 产出。
- **V3 稳定性**：连续回放 ×5 全绿（无 flaky）。
- **V4 lint 有效**：对「无断言」「`source` 缺失或为 `observed:*`」两个反模式输出 reject，退出码正确。
- **V5 可移植性**：`scripts/portability_check.sh` 通过（`core/` `checks/` `skills/` 零业务词命中）。
- **V6 落地可复现**：新机器 `git clone && make demo` 一条命令跑绿。
- **V7 提示词两段式可走查**：每条 `skills/` 下的 skill 都有 `advisory` 标注（A 组 false / B 组 true）；
  正文里不出现任何具体平台/仓库/真源名，只有占位符；`adapters/instance/` 里的实例片段能
  被走查证明「换掉它就能落到另一个项目」。**逐条列一份 skill × 占位符覆盖表**作为验收产物。
- **V8 可机械化的闸已下沉**：`checks/` 三个脚本各自有自测——喂一份**故意漏跑**的清单、
  一份**只写「符合预期」**的结果、一条**`source: observed:*`** 的断言，都必须非零退出。

## 6. 风险与未决

| 项 | 风险 | 处理 |
|---|---|---|
| `events.jsonl` 格式漂移 | browser-harness 是三方工具，升级可能改字段 | **pin 版本**；`transcript/` 承担格式适配；单测用进仓的固定录制样本，不依赖现场录制 |
| 坐标反解成功率 | 复杂组件（canvas、动态列表）解不出 | 用 `UNRESOLVED` 闸显式暴露，不假装能解；兜底 `xy` 必须打标 |
| 录制样本从哪来 | v1 需要真实录制文件做夹具 | 在靶场上手动跑一次录制，产出样本进 `tests/fixtures/recordings/` |
| 私有仓 CI 额度 | GitHub Actions 私有仓有分钟数限制 | v1 只跑机制层单测（快），靶场 demo 不上 CI 或按需触发 |
| 后续三轨的接口 | 「租户池」「状态构建器」这类概念剥离业务后要重命名（如「资源租约池」） | **不在 v1 定**；等第二条轨真开工再定，避免定错 |
| 🔴 **流程型提示词没有强制力** | B 组 skill 是 advisory，agent 不照做不会有报错；容易写成「必须」而自欺 | 能机械化的五道闸一律下沉成 `checks/` 脚本（V8 自测）；剩下真正只能靠判断的才留提示词，并在头部标 `advisory: true`。**不做"靠自觉"的体检表** |
| 五道闸的机械化程度被高估 | 闸②「证据够不够」、闸③「假绿指纹」本质需要理解语义，脚本只能做字段存在性检查 | 明确划成「✅ 可机械化 / 🟡 半 / ❌ 解释器」三档（§4.6 已标注），不假装脚本能判语义 |
| 提示词剥离时丢掉了「为什么」 | 只搬规则会退化成体检表，agent 记不住就失效 | reference 文档保留**模式 + 通用识别法 + 反例**三段式，规则永远带理由；不带理由的规则不入仓 |
